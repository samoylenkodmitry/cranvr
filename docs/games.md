# Games

## Games

Games need Wine with cranvr's DXMT fork and BasaltVR's OpenXR runtime. The app's Play tab has one button, "Set up games". It runs the steps that the Mac still lacks, in this order, with a line of progress for each step:

1. Rosetta 2, which runs Wine's Intel code. macOS asks for an administrator's password. The Play tab says so before the button is pressed.
2. Game support: the app downloads `cranvr-game-support-macos.tar.xz` (about 320 MB) of the release at https://github.com/samoylenkodmitry/cranvr-game-support that `scripts/game-support-version.txt` names. It checks the archive against the SHA-256 in `scripts/game-support-sha256.txt`, unpacks it and installs it with `setup-wine.sh`. It takes about 1.2 GB on disk. `scripts/install-game-support.sh [ARCHIVE]` does the same without the app.
3. Steam for Windows. At the end the Steam window opens. The user signs in there once.

A failed step keeps its message on screen with a Retry button, which runs the steps that are not done. Games on another disk need no setting in cranvr: in the Steam window, Settings, Storage adds a folder on that disk. The Play tab lists the games of every Steam library folder.

The game support has a version, a date such as `2026.11.19`, in `scripts/game-support-version.txt`. `package-game-support.sh` puts it into the archive as `VERSION`. `setup-wine.sh` stamps it into `wine/game-support-version.txt` in the config folder after a good install. When the stamp is older than the app's version, or missing, the Play tab shows "Update game support". After a change of a runtime, DXMT, OpenComposite or Wine patch: set a new date in the version file, run `build-basaltvr.sh`, `build-opencomposite.sh`, `build-wine.sh`, `build-steamvr-driver.sh` and `package-game-support.sh`. Publish the archive, its `.sha256`, `cranvr-opencomposite-source.tar.xz` and `cranvr-wine-source.tar.xz` as a release of the public repository, tagged `v` plus the date.

To build game support from source instead (about an hour, mostly LLVM):

```bash
xcodebuild -downloadComponent MetalToolchain
softwareupdate --install-rosetta
brew install cmake meson ninja mingw-w64 bison
scripts/build-basaltvr.sh
scripts/build-opencomposite.sh
scripts/build-wine.sh
scripts/setup-wine.sh third_party/basaltvr/src
```

`build-basaltvr.sh` clones BasaltVR at a pinned commit into `third_party/basaltvr/src`, applies cranvr's patches and builds the OpenXR runtime and the DXMT fork. `build-opencomposite.sh` clones OpenComposite at a pinned commit into `third_party/opencomposite/src`, applies cranvr's patches and builds `vrclient_x64.dll` with the same MinGW-w64 toolchain (a minute). `build-wine.sh` clones Wine at the tag `wine-11.10` into `third_party/wine/src`, applies cranvr's patches and builds the nine files of Wine that the game support replaces (about two minutes, under Rosetta 2): `wined3d.dll`, which holds Wine's HLSL compiler, `winemac.so` and `opengl32.so`, which run an OpenGL game that asks for the compatibility profile, `wininet.dll`, `wtsapi32.dll`, which SteamVR asks for the lock state of the screen, `user32.dll`, which SteamVR's dashboard needs to start, `ntdll.so`, `winecoreaudio.so`, which gives games the microphone, and `winevulkan.so`, which lets a Vulkan game's images lie on IOSurfaces (see `third_party/wine/README.md`). `build-steamvr-driver.sh` builds cranvr's SteamVR driver into `target/steamvr-driver/cranvr`. `setup-wine.sh` puts Wine 11.10 with the DXMT fork in `~/Library/Application Support/cranvr/wine`, registers the runtime in the Wine prefix, installs OpenComposite as `C:\opencomposite` and the SteamVR driver as `C:\cranvr\steamvr`. It puts the patched files into the engine and the DLLs also into the prefix. It checks the runtime, OpenComposite, the HLSL compiler (it compiles a shader with `isnan`), OpenGL (`gl_compat_check.exe` draws with GLSL 1.10 in the context that Google Earth VR asks for) and Vulkan (`metal_texture_check.exe` reads an IOSurface through a Vulkan image). `scripts/package-game-support.sh` packs the built trees into the archive, its `.sha256` and the sources of OpenComposite and of the patched Wine files in `target/game-support`.

Start the host first: it writes `runtime-control.txt` into its config dir. Then start a game from the window or with the script:

```bash
scripts/run-game.sh 'C:\basalt\runtime\d3d11_runtime_smoke.exe' --render-frames 7200 --visual
```

The smoke program draws a green marker at the left controller and a pale grid. A squeeze of the left grip grows the marker and sends a haptic pulse.

### Steam games

Steam runs in the prefix with BasaltVR's web helper shim (`scripts/setup-steam.sh`):

1. In the window's Play tab, press "Open Steam" (after "Set up games" it has opened Steam already). Log in. Install the game.
2. The tab lists the installed games. Press "Play" next to one: the window starts it by its .exe with the host's environment.
3. Without the window, start Steam with `scripts/run-game.sh --steam`. While Steam runs, start the game by its .exe: `scripts/run-game.sh 'C:\Program Files (x86)\Steam\steamapps\common\Beat Saber\Beat Saber.exe'`.

A rebuild of BasaltVR gives the web helper shim new bytes, and an update of the game support brings them to the prefix. A file check or an update of Steam puts Valve's helper back. The app puts the shim back by itself before each start of Steam and writes a line in the Log tab. Valve's helper then goes to the backup beside it, which the shim starts. The Play tab asks for "Set up games" only when the helper is missing, or when it is neither Valve's nor a shim with that backup. `scripts/run-game.sh --steam` does not repair the helper: run `scripts/setup-steam.sh` first when Steam's window stays black. Do not use `steam.exe -applaunch`: a game that Steam starts gets Steam's environment, not the one with the runtime's control file. For a game under `steamapps\common` the script and the window find the Steam app ID in Steam's `appmanifest` files and set `SteamAppId`, which the game's Steam check needs.

### Games from a folder

A program that Steam does not list, such as a copy of a Steam game with mods, joins the Play tab through "Add a game from a folder" in the card "Other Windows programs". Choose the program's .exe. The app saves the game in `app.json` (`added_games`: its name, which is its folder's name, and the program's Mac path) and lists it with Play, Options and Remove, as it lists a Steam game. The console in VR lists it by its name too. Remove takes the game out of the list with its options and deletes no file. A name that a Steam game or an earlier game uses gets a number.

cranvr reads the program's folder once, when the game is added, and fills in the launch option "Steam app ID" (`steam_app_id`) with its reason in the Options panel. The user can change it (a changed value loses its reason). The game's Steam check asks for the ID. cranvr takes it from `steam_appid.txt` next to the program, else from the Steam game that the folder is a copy of: a Steam game with the same program name whose folder holds at least four fifths of the files and folders of the original (and at least three). A copy has no manifest of its own. The app sets `SteamAppId` and `SteamGameId` from the option, and starts Steam first for a game that has an ID. `scripts/run-game.sh` reads the same option from `app.json`. `CRANVR_STEAM_APP_ID` sets it for one start. Without an option, a program under a Steam library's `steamapps\common` gets the ID of its install folder's manifest, as before.

cranvr sets no Wine DLL override for such a game. A copy of Beat Saber with BSIPA holds BSIPA's `winhttp.dll`, and the guides for Wine and Proton name `WINEDLLOVERRIDES=winhttp=n,b` for it. BSIPA has patched the game's own files, so it starts without the override. With the override it starts twice, and its log reports sharing violations on its own files. A mod loader that does not start without the override gets it from the user, in the field "Wine DLL overrides" of the Options panel.

The runtime speaks OpenXR with Direct3D 11 and Vulkan (see "Vulkan games"). A game that uses OpenVR runs through OpenComposite (see "OpenVR games"). A Steam game starts the program that Steam would start: the launch entry of the game in Steam's app cache, `appcache/appinfo.vdf` (binary KeyValues, version 29, `app/src/appinfo.rs`), with its arguments and its working folder. Of the entries for Windows it takes the first of type `vr`, then a plain one, then another choice of Steam's dialog. It leaves out entries for a 32-bit system, a beta branch, a DLC or another realm, and entries whose program is no `.exe` file in the game's folder. The Lab starts as `TheLab\win64\TheLab.exe -popupwindow`: the largest program of its folder is `SecretShop.exe`, one of its side experiences. An entry without a working folder starts the program in its own folder, as before; which folder Steam itself takes then is not measured. A game that Steam's cache does not know, such as a game added from a folder, starts the program that the app finds in its folder: three folders deep, preferring a 64-bit folder.

A game that the app or `scripts/run-game.sh` starts draws nothing into its Mac window: `DXMT_SKIP_PRESENT=1` (cranvr's DXMT patch 0008) sends each frame's GPU work without the present but tells the game that the present worked. `CRANVR_MAC_MIRROR=1` for the script draws the window again.

### OpenVR games

Most SteamVR games speak OpenVR. Each game's launch options choose its OpenVR runtime: OpenComposite (the default), SteamVR (see "SteamVR games") or none. The game support installs [OpenComposite](https://gitlab.com/znixian/OpenOVR) as `C:\opencomposite` (GPL 3, built from source by `scripts/build-opencomposite.sh`). It is an OpenVR runtime that makes OpenXR calls, here to BasaltVR's runtime, which is the active OpenXR runtime of the prefix.

A game finds OpenComposite through the prefix's OpenVR path file, `%LOCALAPPDATA%\openvr\openvrpaths.vrpath`. Valve's `openvr_api.dll`, which every OpenVR game carries, reads it and loads `bin\vrclient_x64.dll` from the runtime that it names. No file of a game changes. An OpenXR game ignores the file. Steam reads the file too: with SteamVR installed, Steam starts OpenVR as its VR watchdog about 8 s after its own start, from the runtime that the file names, and it writes its own paths into the file. So the file names a game's runtime only while the game runs (`app/src/openvr.rs`, `app/src/game_run.rs`). The app writes it when it starts a game and puts the file from before back when the game ends: when no process of the game's folder runs any more, so a launcher or a mod loader that starts the game again counts as the same run. While no game runs, the file names SteamVR when the Steam library has it, or no runtime: a Steam start puts one of them in place of a file that names OpenComposite. A game started with Off finds no runtime. `scripts/run-game.sh` follows the same rule: `CRANVR_OPENVR=opencomposite`, `steamvr` or `off` chooses for one start, else the setting `wine.openvr` of `app.json` (`opencomposite` by default), and `--steam` gets SteamVR or no runtime. A Steam start during a game's run still finds OpenComposite, as the Play button starts Steam and then the game: OpenComposite refuses Steam's watchdog with an error and no message box (its patch 0011).

The choice is OpenComposite by default and visible in four places: "OpenVR games" in the Settings tab and in the Wine card, a row "OpenVR" in each game's options with "As in Settings", "OpenComposite", "SteamVR" and "Off", and each game's row in the console in VR. A game's own choice is `openvr` in its entry of `launch` (`opencomposite`, `steamvr` or `off`), absent when it follows the setting.

A game that draws nothing through OpenComposite gets SteamVR (`app/src/game_run.rs`, `app/src/vr_system.rs`). A run of a game through OpenComposite watches the host's status lines: the game's sessions and its frames. It drew nothing when OpenComposite's log of the run names the game's folder, no frame reached the host and cranvr did not stop the game, and one of three holds. OpenComposite stopped the game (its log shows an abort: The Lab stops so with "Cannot create DX texture swap chain" and a message box on the Mac, and the verdict came 5.3 s after the Play button). The game closed its last session and opened none for 10 s while it kept running. The game ended by itself. The last two need a stats window with no game frame while the game held a session, as the host counts frames only while a headset streams. A game that follows the setting then gets SteamVR as its own choice, with the reason "cranvr picked SteamVR because the game drew nothing through OpenComposite.", which the Play tab shows. The window and the console show a notice. A game that OpenComposite stopped hangs in the message box, so the app ends it and starts it again through SteamVR at once. A restart of a game in SteamVR waits until SteamVR has quit after the old run (up to 8 s; it took about 3 s), because a game that starts while SteamVR quits gets `VRInitError_Init_ShuttingDown`: The Thrill of the Fight crashed on it with a Unity dialog. Under Wine SteamVR's quit can stall for minutes on a web helper that it fails to end ("Kill process ... vrwebhelper_systemui because it didn't quit in time"). The app then ends SteamVR's programs before the new start and says so in the Log tab. Any other game takes SteamVR at its next start. A game whose choice the user made keeps it, and the notice says to try SteamVR. Without SteamVR in the library nothing changes, and the notice says to install it. A change of the choice in the Play tab or in the console clears the reason.

What the port to Wine needed, in `third_party/opencomposite/patches` (see its README):

- OpenComposite builds for Windows with MSVC. The build here uses MinGW-w64 with Direct3D 11 and Vulkan (its patch 0012, see "Vulkan games"). An OpenGL game's textures are copied into Direct3D 11 images (see below).
- MSVC and GCC pass the address of a returned struct and `this` in the other order. A virtual method such as `GetProjectionMatrix`, which an MSVC game calls, would write its result over the interface object. The generated interface classes pass the address as a parameter.
- The runtime offers images of the order B8G8R8A8 only, and many games draw R8G8B8A8. OpenComposite copies such a game's image into the runtime's image with a draw.
- The runtime offers the STAGE space, which is the LOCAL space with the floor at height 0 (runtime patch 0007). OpenComposite needs it for the standing space of OpenVR.
- A game that sets an action manifest (IVRInput) needs runtime patch 0008. OpenComposite creates its action sets once. It attaches them to its first OpenXR session, destroys that session when the game submits its first frame (it makes a new one on the game's own graphics device) and attaches the same sets to the new session. The runtime refused the second attach.
- OpenComposite builds the OpenXR bindings from the game's default bindings. It loads the file for the Touch controller (`oculus_touch`) when the manifest names one. Without it, OpenComposite takes the best of the other files, and its patch 0003 maps the Vive wand's trackpad to the Touch thumbstick. `scripts/e2e.sh --openvr-actions touch|vive|both` tests a manifest with each.
- The runtime offers `XR_FB_display_refresh_rate` with the headset's rate as the only rate (runtime patch 0009). OpenComposite answers the display frequency of the headset from it (its patch 0004). It answered 90 Hz before.
- The runtime's log lines (runtime patch 0010) say which actions a game binds and the first input that reaches each of them. They go to the game's stderr: the cranvr app keeps them in `game.err.log` of the config folder, and a Unity game keeps them in its own `Player.log`. Steam keeps no stderr of a game that it starts, so runtime patch 0011 also appends the lines to `game-input.log` in the config folder (beside `runtime-control.txt`; it keeps the lines of the last runs, up to 256 KB). OpenComposite writes its own log to `drive_c/users/<user>/AppData/Local/OpenComposite/logs/opencomposite.log` in the prefix. Its patch 0006 adds a line there when the source of a controller's pose changes (the runtime's grip pose, a held pose, the hand tracking fallback or no pose), and keeps a controller where it was for a moment when the runtime has no pose of it. Its patch 0007 gives the headset and each controller a serial number of its own: a game that tells its controllers apart by their serial numbers (Serious Sam VR does) took two controllers that both said `<unknown>` for one, and the right one never worked. SUPERHOT VR's `Player.log` shows 3 action sets with 50 actions, 17 of them bound for the Touch controllers (34 bindings), and the probe's right trigger at 0.75, A, left grip and the stick at 0.5 reaching the game's actions.
- OpenComposite runs scene applications only. For another application type it showed a message box, and Steam's VR watchdog (type 6) waited in that box until Steam's own watchdog ended Steam after 15 s. Its patch 0011 refuses such a type with `VRInitError_Init_InvalidApplicationType` and one log line. `openvr_smoke.exe --app-type watchdog` checks it after each install.
- An OpenGL game (Google Earth VR, built on Google's ION) needs four changes. macOS has no compatibility profile of OpenGL 3.2 and newer: Wine's Mac driver makes the core context for such a request (Wine patch 0002). The core profile does not compile GLSL 1.10 or GLSL ES 1.00, so Wine's `opengl32` gives such a shader a preamble of GLSL 1.50 (Wine patch 0003). The game loads its pictures with WinINet on several threads, and Wine's WinINet crashed when two threads closed handles at a time (Wine patch 0004). OpenComposite reads each eye of the game's OpenGL texture into a pixel buffer and copies it into the runtime's Direct3D 11 image one frame later (its patch 0009, 0.7 to 0.95 ms per eye). Earth VR makes 72 frames a second at 72 Hz in a test host. See `third_party/wine/README.md` and `third_party/opencomposite/README.md`.
- A game without an action manifest reads the legacy controller state and takes its clicks from the button events of that state (`VREvent_ButtonPress` and its kin). OpenComposite's OpenXR port sent none of them (its patch 0010 sends them). Google Earth VR started its welcome tour 4 seconds after a trigger press with the patch, and never in 13 presses without it.
- A game that sends a pulse with no amplitude in every frame (SUPERHOT VR stops the haptics of its hands about 130 times a second) cost the host and the headset a datagram each time. The host sends only the first stop after a pulse (`forwards_haptic` in `runtime_link.rs`); the probe reported 9398 of 9402 pulses without amplitude in one minute.

OpenComposite takes the hidden area mesh from `XR_KHR_visibility_mask`, which the runtime lacks, so it returns an empty one, as OpenVR allows. It leaves out overlays and the keyboard of OpenVR (OpenComposite patch 0008): the runtime takes no quad layer, so a loading screen that an OpenVR game shows as an overlay does not appear, and the game's frames go on. It supports games with 64-bit Direct3D 11, Vulkan or OpenGL programs and 8-bit images. A 32-bit game, a Direct3D 12 game and a game with 10-bit or float images are not supported. An OpenGL game's frames pass through the CPU and reach the headset one frame later than a Direct3D 11 game's.

OpenComposite answers the interfaces of the OpenVR SDK up to 2.15.6 (its patch 0013). A game built with a newer SDK asks for newer versions: Half-Life: Alyx (SDK 2.16.0) asks for `IVRSystem_026`, `IVRCompositor_029`, `IVROverlay_028` and `IVRInput_011`, which SDK 2.15.6 has, and for `IVRIPCResourceManagerClient_004`, which no public SDK has. An interface that OpenComposite lacks gets `VRInitError_Init_InterfaceNotFound` and a line in its log, as from SteamVR. The game decides whether it goes on without it: Half-Life: Alyx does. Before the patch OpenComposite showed a message box "Missing interface" on the Mac and stopped the game once the box closed.

Half-Life: Alyx (Source 2, Direct3D 11 by default) runs through OpenComposite and through SteamVR. Its first level (`+map a1_intro_world` under "Arguments" starts it at once) drew its first frame 21 to 27 s after Play through OpenComposite and 53 to 63 s after Play through SteamVR, in a test host at 120 Hz with the probe and a game render size of 70%. Through OpenComposite the level made 480 to 600 game frames in each 5 s window (median 534, 107 frames a second) at a load average of 8 to 17. The game's own loop sets that rate: `xrWaitFrame` waited 0.01 to 0.3 ms, and the time from `xrEndFrame` to the next `xrWaitFrame` was 7.1 to 9.8 ms (`scripts/perf/xr-frame-timing.sh`). At a game render size of 50% the same part of the level made 447 to 575 frames a window (median 501): fewer pixels did not raise the rate. The game, an x86-64 program under Rosetta 2, kept 2.6 cores busy. The game sizes its images itself with its "auto fidelity" (`vr_fidelity_level_spew 1` logs it): from 0.81 to 1.416 times the recommended size, and 4x MSAA despite cranvr's limit of 2 ("the game made a 4x MSAA texture despite the limit" in the game's log). Through OpenComposite the game reads a fixed 9.0 ms from `GetFrameTiming`, so it stays at its lowest level, 0.81. Through SteamVR it reads SteamVR's measured times and climbs to 1.416: there the compositor's GPU work finished 5.0 to 5.4 ms late, and SteamVR presented 453 to 487 frames a window in the game's opening scene. At SteamVR's manual scale 1.5, the 1.5 times the area that SteamVR's own factor gives on this Mac (#193), the game's top level made images of 1512x1614 against 1234x1319. The compositor's GPU work then finished 6.8 to 7.6 ms after its draw against 4.7 to 6.7 ms. The game made 327 to 414 frames a window against 292 to 419 at a load average of 14 to 19 (#195). The game pauses while SteamVR's dashboard is open. In one of five SteamVR starts of the level, the dashboard stood open when the level's first frame came, and the game stayed paused for the rest of the run. Steam for Windows ended 5 to 18 s after the game ended in each of eight SteamVR runs. It ended in none of nine OpenComposite runs (#197). The game reads its auto fidelity from OpenComposite's fixed frame timing (#198). A game that cranvr starts while Steam runs gets no Steam Cloud download at its start: Steam downloads the files at its own start (#199).

A game folder with OpenComposite's own `openvr_api.dll` or an `opencomposite.ini` from another setup bypasses the choice: the game loads that DLL, not the runtime in the prefix. Put Valve's file back. OpenComposite stops a game with a message box for an option that it does not know, such as a section header in the `.ini`.

### Vulkan games

A Vulkan game runs on MoltenVK, which Wine's `vulkan-1.dll` reaches through `winevulkan.so`. An OpenXR game gets `XR_KHR_vulkan_enable` and `XR_KHR_vulkan_enable2` from the runtime (runtime patch 0013). An OpenVR game submits its Vulkan images to OpenComposite (its patch 0012), which puts them into the runtime's images on the GPU. The runtime's images are Vulkan images on Metal textures of IOSurfaces (Wine patch 0009). cranvr-host encodes the game's picture from those IOSurfaces with no copy through the CPU, as it does for a Direct3D 11 game.

The cost of each path at 120 Hz, from the runtime's note on the GPU's finish after `xrEndFrame` (`scripts/e2e.sh --xr-vulkan` and `--openvr-vulkan` with the probe, two eyes of 1444x1546):

- An OpenXR program with a swapchain per eye: 120.0 to 120.1 frames a second. `xrEndFrame` took 0.04 ms, its fence 0.01 ms, and the GPU finished a frame 0.7 to 0.8 ms after `xrEndFrame`.
- A swapchain of two slices: the runtime copies each slice into an IOSurface image. `xrEndFrame` took 0.16 ms, and the GPU finished 1.41 ms after it, about 0.6 ms later.
- An OpenVR program through OpenComposite: 1.33 ms for B8G8R8A8 images, which OpenComposite copies, 1.40 ms for R8G8B8A8 images, which it blits, and 2.72 ms for 4x MSAA images, which it resolves first. Each made 120.0 to 120.1 frames a second.

On a Quest 3 at 120 Hz and 2064x2208 per eye, the OpenXR program made 119.7 frames a second (598 and 594 game frames in the host's 5-second windows), and the GPU finished a frame 1.4 to 1.5 ms after `xrEndFrame`. The OpenVR program made 120.0 frames a second after its start (601 and 600 in the windows), with the blit, and the GPU finished 1.9 ms after `xrEndFrame`.

Each game's options have the row "Graphics" with "Game's own", "Direct3D 11" and "Vulkan" (`graphics` in the game's entry of `launch`: `direct3d` or `vulkan`, absent for the game's own choice). A choice adds an argument at the game's start: the text of "Vulkan arguments" or "Direct3D 11 arguments" under Advanced (`vulkan_args` and `direct3d_args`), else the argument of the game's engine. cranvr knows three engines by their files, never by the game: Unity (`UnityPlayer.dll` or a folder `<program>_Data` next to the program: `-force-vulkan` and `-force-d3d11`), Unreal Engine (the folder `Engine/Binaries`: `-vulkan` and `-d3d11`) and Croteam's Serious Engine (`Content/CachedShaders_VLK.gro`: `+gfx_strAPI VLK` and `+gfx_strAPI D3D11`). The line under the choice says which argument the game gets and where it comes from. The console in VR shows the choice too. `scripts/run-game.sh` applies no choice: give the argument after the program.

Serious Sam VR: The Last Hope, an OpenVR game of the Serious Engine, draws with Vulkan through OpenComposite. Its log says "Gfx API: Vulkan". The game holds its loading scene, which it shows for about a minute after its start, at 99 frames a second with both APIs (issue #155). Its quality presets (`Content/SeriousSamTLH/Config/GPU-QL2.cfg` to `GPU-QL5.cfg`) set the console variable `men_iMaxAllowedFPS` to 99. The loading scene runs at that cap. Its menu and its first level run at or near the headset's rate. The game's frames in a test host at 120 Hz with the probe, at a load average of 4 to 26. The game ran at nice 5 in these runs, except where the table says nice 0 (see below):

The timing layer of `scripts/perf/xr-frame-timing.sh` (see "Measure a game with a Quest on the desk") shows where the time of a frame goes. In the loading scene with Vulkan, `xrWaitFrame` waited 0.00 ms: each frame came after the runtime's next point of the display. A frame took 10.1 ms: 7.6 ms from the return of `xrWaitFrame` to `xrEndFrame` and 2.5 ms from `xrEndFrame` to the next `xrWaitFrame`. In the menu `xrWaitFrame` waited 0.2 to 0.6 ms. The time outside `xrWaitFrame` took the other 7.7 to 8.1 ms of the 8.33 ms (4.1 to 4.4 ms and 3.6 to 3.8 ms). That time holds the game's work and OpenComposite's, such as its copy of each eye at the submit. The runtime's note said that the GPU finished a frame 2.3 to 3.3 ms after `xrEndFrame` in the loading scene and 4.6 to 6.3 ms in the menu. `scripts/run-game.sh` started the program as a background job of zsh, which runs it at nice 5, while the cranvr app starts a game at normal priority. In the first level at nice 5, `xrWaitFrame` waited 0 to 1.1 ms. The time outside it was 2.1 to 3.1 ms before `xrEndFrame` and 5.2 to 6.0 ms after it, so the game lost frames to the Mac's other work (#163). At nice 0 the level made 118.2 to 120.0 frames a second over 40 s at a load average of 7 to 14. `xrWaitFrame` then waited 0.4 to 2.7 ms. The script now runs the program at normal priority. The game can start a level by itself: `+gam_strLevel Content/SeriousSamTLH/Levels/01_TLH/Earth/Earth_01.wld` loads it after the menu. The game takes about 25 s to its first frame and 85 to 135 s to its menu.

The argument `+men_iMaxAllowedFPS 120` in a game's Arguments lets the loading scene run at the headset's rate, which a loading scene does not need. With Vulkan the game runs its AutoDetect about 12 s after its start and applies its presets again, so the cap goes back to 99. It does so when the hardware line of its saved settings differs from what the API reports. The line came from Direct3D 11. A game that a test ends saves no settings. On the Quest the game reached only its loading scene, at the same 99. The game asks for images 1.118 times its view size (its `vr_fRenderingPixelRatio`). With a full Quest 3 eye (2064x2208) at a game render size of 100% that is 2307x2468. The runtime refused such images before runtime patch 0018, and OpenComposite stopped the game with a message box "OpenComposite Error - info in log" (#164). The runtime now takes images up to 4128x4416, twice a Quest 3 eye. In a test host at 120 Hz with the probe, Direct3D 11 and a full eye at 100%, the game made swapchains of 2307x2468, held its loading scene at 94 to 99 frames a second and made 100 to 107 in its menu, with three windows at 85 to 90, at a load average of 5 to 28. At 70% the menu made 119 to 120 (#155): at 100% the menu has twice the pixels and stays below the rate. Beat Saber 1.46 has no Vulkan: its Unity player was built without it, and with `-force-vulkan` it ends at its start ("Forced GfxDevice 'Vulkan' was not built from editor").

### SteamVR games

A game that needs SteamVR itself (its menus, its overlays, its input bindings, or a check for SteamVR) runs in SteamVR for Windows under Wine with the launch option "OpenVR: SteamVR". SteamVR (app 250820, free) comes from the user's Steam library in the prefix. The game support installs cranvr's SteamVR driver as `C:\cranvr\steamvr` (`steamvr/driver_cranvr.cpp`, built with MinGW-w64 by `scripts/build-steamvr-driver.sh`). The OpenVR path file names SteamVR as the runtime and the driver's folder in `external_drivers`, so the game's `VR_Init` starts SteamVR, as on Windows, and SteamVR loads the driver. The game list leaves SteamVR out: it is a runtime, not a game.

The driver speaks the control protocol of BasaltVR's runtime with the host (`host/src/runtime_link.rs`), over the same control file (`BASALT_CONTROL`, which SteamVR inherits from the game):

- `IServerTrackedDeviceProvider` adds a headset and two Touch controllers. The headset has a display component (no lens: the identity distortion, the field of view and the eye distance of `VIEW_CONFIG`) and a direct mode component. The controllers use SteamVR's own Touch profile (`{oculus}/input/touch_profile.json`) and render model; their raw pose comes from the grip pose and the model's `openxr_grip` component. Buttons, axes, haptics (`/output/haptic`) and the headset's proximity follow the host's messages.
- The direct mode component gets SteamVR's layers for each frame. It acquires the keyed mutex of the compositor's sync texture, so its GPU waits for the compositor's draws, and draws the layers into three pairs of images that it shares with the host as IOSurfaces (DXMT's export), with no copy through the CPU. A thread of the driver waits for that GPU work and sends `FRAME_READY` with the host's timestamp of the head pose that SteamVR drew with. It sends SteamVR a vsync event each period of the headset's rate.
- After a crash of its server SteamVR turns the drivers off (`blocked_by_safe_mode` in `steamvr.vrsettings`). cranvr turns its driver on again before it starts a game with SteamVR, and says so in the Log tab.
- The first process whose layers reach a frame and that is not SteamVR's compositor is the game. The driver writes its program into `game-program.txt` beside the control file and connects again, so the host names the game. When the game ends, the driver asks SteamVR to quit (`VREvent_DriverRequestedQuit`): SteamVR starts with each game and ends with it.
- The driver sets `Prop_GraphicsAdapterLuid_Uint64` of the headset to the first DXGI adapter, where SteamVR's panels make their Direct3D devices.
- SteamVR multiplies the size that a driver recommends by a factor of its own, which it takes from a measurement of the GPU. With The Thrill of the Fight it gave the game 1068x1144 for a recommended 874x934 ("Clamping render target scale to 1.5x total area", #193). The driver turns on SteamVR's manual render scale at each start (`supersampleManualOverride` in the `steamvr` section of `steamvr.vrsettings`, through `IVRSettings`), so cranvr's game render size decides a game's size in SteamVR too. It does so also when Steam or `scripts/run-game.sh` starts SteamVR. The manual scale (`supersampleScale`) is 1 unless the user set another one on SteamVR's settings page. SteamVR lets no driver change that value ("Blocking driver cranvr attempt to set setting steamvr/supersampleScale" in `vrserver.txt`). The driver's log says when it turned the manual scale on and names a scale other than 1. SteamVR rounds a recommended size down to a multiple of 4, so the driver recommends such a size. At a game render size of 70% with foveation Off at 120 Hz, the game's images are 872x932 in SteamVR (`vrserver.txt`: "HMD driver recommended: 872x932", the driver: "games render 872x932" and the game's swap textures of 872x932), against 874x934 through OpenComposite.

What SteamVR needed under Wine and DXMT:

- Wine patch 0006: Wine answered no question about the session's lock state. SteamVR's compositor took the screen as locked, marked the head's pose of every frame invalid and faded the picture out.
- Wine patch 0007: Wine's `user32.dll` had no `DwmGetDxSharedSurface`. SteamVR's dashboard imports it through `vrdesktop.dll` and did not start without it, so the menu button opened nothing.
- DXMT patches 0013 to 0018 (see `third_party/basaltvr/README.md`): buffers and textures that processes share, a keyed mutex and the DXGI usage that Chromium's GPU process asks for, a desktop duplication that delivers no frame, a swapchain for a window of another process and textures that a process opened and shares again. SteamVR's compositor and its Chromium panels need them.

`scripts/e2e.sh --steamvr` runs `openvr_smoke.exe` through SteamVR and the driver and checks both eyes, the controllers' buttons and poses and a valid head pose in 90 percent of the frames.

The menu button of the left controller opens SteamVR's dashboard over the game, as on Windows.

### What the host and the app do for a game

Neither the host nor the app knows a game by name. A game's quirk is a launch option (`app/src/launch.rs`, shown in the Play tab), set by the user or by cranvr with a reason shown in the window.

- **Render size.** `--game-scale F` (default 0.7, "Game render size" in the Settings tab) makes a game render each eye at this share of the stream's eye size. A game reads its size once, at its start. Before any headset links, the host writes the eye that a Quest 3 would get from the host's settings (refresh rate, foveation, eye width) at the game render size, through the negotiation of a link (`host/src/game_eye.rs`, #170). At 120 Hz with foveation Off and 100% that is 1248x1306. With Medium and 70% it is 1176x1232. Before #170 the host wrote a whole Quest 3 eye of 2064x2208 there, 2.8 times the pixels of the stream's eye at Off and 100%. A headset with another eye writes its own size at its link. A game that runs then keeps the size of its start: the window and the console in VR say so, with both sizes. The host keeps a render size per game. It judges a game by its whole run (#167): it keeps the game's frame rate of each stats window from 20 s after the game connects, and it decides when the game disconnects. A run of at least 5 minutes (60 windows) whose median window is below 95% of the headset's rate gets a smaller share at the game's next start. A shorter run decides nothing. A game shows its loading scene for a fixed time at each start, and the user plays for the rest, so the median of a long run is the rate of play. Serious Sam VR holds its loading scene for 60 to 90 s at 99 frames a second by its own cap, with dips to 47 while it loads (see "Vulkan games", #155). The host judged only the first minute before and gave the game a smaller size for that scene. A run that ends with the host, such as at a restart for a new setting, decides nothing either. The step aims 10% under the rate, with a floor of 40%. When a smaller size did not raise a game's rate by 5%, the size does not limit the game: the host gives it the share from before that step back and lowers it no more. The runtime names the game in `game-program.txt` and reads the shares from `game-sizes.txt` in the config folder. cranvr's SteamVR driver reads them too: it runs in SteamVR's server, which inherits `CRANVR_GAME`, the game's program, from the game that starts SteamVR. The Settings tab lists the learned sizes and forgets them. A game that makes fewer frames than the headset's rate adds 10 to 18 ms of latency. The host warns in the log 20 seconds after the game connects when the game stays below 95% of the rate.
- **Anti-aliasing.** Games under Wine use at most 2x anti-aliasing by default ("Game anti-aliasing" in the Settings tab, `CRANVR_MAX_MSAA` for `scripts/run-game.sh`, 0 for no limit). cranvr's DXMT patch then reports 4x and 8x as unsupported, so a game that checks picks 2x. It applies when a game starts. A game started from the Steam window gets it after Steam restarts.
- **Mac window.** A game's own window on the Mac shows no picture while "Game window on the Mac shows the picture" is off (`DXMT_SKIP_PRESENT=1`). A Unity game opens that window over the whole main display: The Thrill of the Fight (Unity 2021.3) opened a window of 3840x2160 at 0,0 on a 3840x2160 display and kept it until its end (#192). The window covered the desktop, which the headset's desktop panel shows. Each game's options have the row "Mac window" with "As in Settings", "Small" and "Game's own" (`window` in the game's entry of `launch`: `small` or `own`, absent when it follows the setting). As in Settings means a small window while the window shows no picture and the game's own window while it shows the picture. Small adds the arguments of the game's engine, which cranvr knows by its files (see "Vulkan games"). Unity takes `-screen-fullscreen 0 -screen-width 640 -screen-height 360`. The line under the choice says which arguments the game gets and why. In 5 starts of The Thrill of the Fight through OpenComposite and SteamVR the game's window was 640x392 with its title bar, at the top left corner of the display. One start with "Game's own" opened the window of 3840x2160 again. Unity keeps the window of the last start in the game's settings in the registry (`Screenmanager Fullscreen mode` 3, `Screenmanager Resolution Width` 640 and `Height` 360 after a small start). So a game that started with a small window opens the small window again with "Game's own" until the game changes it. `-screen-fullscreen 1 -screen-width 3840 -screen-height 2160` under "Arguments" for one start, with the display's size, put the settings back as they were before (mode 1, 3840x2160, `Use Native` 1). `-screen-fullscreen 1` alone gave a window over the whole display that kept the saved 640x360. Beat Saber sets its window itself: it opened at 640x392 and then made it 1280x752. cranvr knows no measured arguments for the other engines, so their games keep their own windows. Unreal Engine takes `-windowed -ResX=640 -ResY=360` by its own documentation, unmeasured under cranvr's Wine. Half-Life: Alyx (Source 2) opens a window of 1920x1080 (1920x1112 with its title bar) at 960,30 on a 3840x2160 display: a quarter of the display, not the whole display. With `-nowindow` under "Arguments" it opens no window on the Mac, and its frames reach the host as before (566 to 592 frames in 5 s windows at 120 Hz through OpenComposite). cranvr knows no Source 2 engine by its files, so it adds no argument. A user types such arguments into "Arguments" under Advanced. `scripts/run-game.sh` applies no choice either.
- **Panel pixels.** While a game runs, a display in a scaled mode shows its panel's own pixels ("Panel pixels while a game runs" in the Settings tab, on by default, `--keep-display-modes` turns it off). A scaled mode, such as 3008 x 1692 points on a 3840 x 2160 TV, makes macOS draw every change at 6016 x 3384 pixels and shrink it. A helper process (`cranvr-host --unscale-displays`) sets each such display to the panel's pixels with at least as many points, so no window moves, for itself only. When the game disconnects, the host ends the helper. macOS then gives each display its mode back.
- **A black picture.** A game that renders both eyes in one pass into a swapchain with two slices can leave the second slice empty under DXMT. A game of another engine version (Beat Saber 1.44.1 on Unity 6000.0 with the OpenXR plugin 1.14.3) can leave both slices empty. The host finds the symptom (`host/src/eye_check.rs`): about once a second it reads a grid of 64 x 64 pixels from each eye of the game's newest frame. When the left eye has content (at least 8 lit samples) and no sample of the right eye is lit for 4 checks in a row, it sends one `black_eye` status line for the game run. The app answers in `app/src/black_eye.rs`: it turns on the launch option "Each eye in its own pass" for that program, restarts the game and shows a notice in the window and in the console. The option sets `BASALT_MAX_ARRAY_SIZE=1` (runtime patch 0003), so the runtime rejects two-slice swapchains and the game draws each eye into a swapchain of its own. When the picture stays black with it, the app turns it off, turns on "Both eyes in one pass" (`DXMT_RT_ARRAY_INDEX_FROM_ANY_SHADER=1`, DXMT patch 0010) and restarts the game once more. An OpenVR game draws into a texture of its own and hands it to OpenComposite or SteamVR, so "Each eye in its own pass" cannot reach it. A Unity game with the OpenVR provider draws both eyes into one such texture with instanced draws. For a game whose run went through OpenComposite or SteamVR, the app turns on "Both eyes in one pass" at the first report. The host names the game's runtime in the `black_eye` line, and cranvr's SteamVR driver names itself "SteamVR (cranvr driver)" there. OpenComposite's log of the run names the game's folder (`app/src/game_run.rs`). An OpenXR game ignores the OpenVR choice, so its choice decides nothing here. The host also reports a picture that is black in both eyes for 90 checks in a row (`"eye": "both"`), because a game that loads shows a black picture for about 40 seconds before its first scene. The app answers both reports in the same way. A single lit sample in either eye ends the count. A flicker between states never counts. The host also logs the number of lit samples of each eye whenever the state changes ("Eye check: 88 of 256 samples lit in the left eye, 87 in the right eye"), which tells a black picture from a lit one in a test run. A host started with `CRANVR_EYE_DUMP=FOLDER` writes both eyes of the game's newest frame as `eye-left.png` and `eye-right.png` into the folder at each check, so a test run can look at what the game drew.
