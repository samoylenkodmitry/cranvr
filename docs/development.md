# Build, run and test

## Build

```bash
cargo build --release
scripts/build-client.sh            # target/client/cranvr-client.apk
scripts/build-client.sh --install  # and install it with adb
scripts/build-client.sh --phone    # cranvr-phone.apk for an Android phone or tablet
```

`scripts/bundle-app.sh --install` builds `cranvr.app` and installs it in `/Applications`.

## Run

1. Put the Mac and the headset on the same network. Use 5 GHz or 6 GHz Wi-Fi, or the USB cable.
2. Start the window: `./target/release/cranvr`. The host starts by itself.
3. Open cranvr on the headset. The connect panel lists the Macs that run cranvr. Press yours. A headset that the Mac does not know shows a code of six digits. The window on the Mac shows the same code with Allow and Deny. Press Allow when the two codes are the same.

`docs/quest-first-run.md` is the checklist for a first run with Steam and Beat Saber. The window saves its settings in `~/Library/Application Support/cranvr/app.json`. The app reads the file entry by entry. An entry that it cannot read, such as an action name that no action has, keeps its standard value. The window then shows an error that names the entry. A save keeps such an entry as the file has it until the user changes that setting. A file that is no JSON at all stays as it is: the app runs with the standard settings and saves no change. A change of refresh rate, bitrate, foveation or desktop restarts the host. The headset reconnects by itself.

The app watches the host that it started (#148). A host that ends by itself starts again at once. A host that sends no frames for 15 s while a headset is connected with no game starts again too, unless the headset's app paused the stream. A host that ends within a minute of its start waits longer each time it does so again: 0, 2, 4, 8 and 16 s, then 30 s for each further start. The watch never gives up. The Log tab names each start and its reason. A host whose frames stopped says so in the log every 6 s, with the reasons: no new pose, no free buffer or a busy encoder. Each start keeps the last host's log as `host-previous.log` next to `host.log`. The host drops a frame whose command buffer macOS stopped and draws the next frame. macOS stops the host's frames when another process holds or hangs the GPU: "Impacting Interactivity", "Caused GPU Hang Error" or "Discarded (victim of GPU error/recovery)". After several such errors macOS ignores all GPU work of the process: "Ignored (for causing prior/excessive GPU errors)". The host then tries new command queues once. After that it ends with exit code 75. The app then starts a new host. The host also ends after 30 failed frames in a row and when one frame waits 3 s for the GPU. A frame that took more than 100 ms gets a line in the log, at most one in 5 s. `CRANVR_TEST_GPU_STALL=SECONDS` makes one frame of a test host wait for an event that nobody signals, for a test of this watch.

Without the window:

```bash
./target/release/cranvr-host --fps 120 --desktop
```

`cranvr-host --help` lists every option. `--status` prints status lines (`@cranvr` and a JSON object) on stdout for a program that runs the host. `host/src/status.rs` lists them.

### What you should see

With the desktop off, the host shows a test scene:
- a sky with a grid line every 15 degrees and brighter lines every 45 degrees;
- a floor with 50 cm squares and a green line every meter;
- a yellow ball at the left controller and a cyan ball at the right controller;
- a small red square near the left edge of the left eye and a blue square near the left edge of the right eye.

A game replaces the scene while it runs. The headset's Room setting (in its console) decides what fills the view while no game runs. With Passthrough (the default) the room shows around the panels and the client leaves the streamed scene out. With Scene the host's picture fills the view. The launch argument `room` (`scene` or `passthrough`) decides for one launch.

The headset's Interface setting decides how the hand menu and the console draw: 3D (the default) or Flat. It is a row of the console's Headset page and of the headset's page in the Mac's app. In 3D the hand menu and the console's Stream page are Cranpose holograms (`SpatialHologram`, #111): the controls float as objects of glowing glass with no panel behind them. The words stay on a panel at full resolution. On the Stream page each choice shows its value by the form of its objects. The refresh rate is an arc with a tick for each rate and a crystal knob. The bitrate is a row of gems. The chosen gem is larger and stands in a beam. Foveated encoding is a row of flowers whose petals grow from a bud at Off. The game's render size is a row of cubes that grow. The game's anti-aliasing is a crystal between two arrows. A toggle is a capsule whose lit half slides to the chosen side. The page rises out of a projector with a cone of light in 420 ms. Two ribbons and a field of sparks stand beside it. The ball of the hand menu is a still crystal. The other pages of the console are trays of 3D geometry with light and shadows under the words (`SpatialTray`). The headset's Theme setting picks the colors of the 3D menus: Cyan, or Amber with violet glass and a gold chosen option. In passthrough a faint dark glass stands behind each line of words. The title row of the hand menu has a switch "3D". One press there gives the flat menus back. A closed menu composes no hologram and no tray. While a game runs and no controller model shows, the flat ball stands in for the crystal, so the closed menu adds nothing to the game's frame. On a Quest 3 with a stream at 120 Hz and no controller model in view, the Stream page as a hologram took 2.57 ms of the app's GPU and 1.49 ms of the compositor. The same page flat took 1.02 ms and 0.91 ms. The open hand menu took 2.96 ms and 1.72 ms as a hologram, and 1.00 ms and 1.12 ms flat. While a controller model shows, the page adds 0.7 ms and the menu 0.8 ms of the app's GPU. The closed menu costs the same in both interfaces. The frame rate stayed at 120 Hz, with at most one second at 119 in a case of 4 s, in both interfaces (`scripts/ui3d-budget.sh`). The launch argument `interface` (`3d` or `flat`) decides for one launch. The launch argument `theme` (`cyan` or `amber`) picks the colors for one launch.

## Test without a headset

```bash
cargo test --release
cargo test --release -p cranvr-app -- --ignored
cargo test --manifest-path client/Cargo.toml
./target/release/cranvr-host --config-dir /tmp/cranvr-test &
./target/release/cranvr-probe --seconds 10
./target/release/cranvr-probe --seconds 10 --tcp            # media over TCP, as over USB
./target/release/cranvr-probe --seconds 10 --drop-percent 3 # lets the parity recover packets
```

The probe is a client of the protocol on this Mac. It connects to port 9950, sends a head that turns 20 degrees a second and scripted controllers once per refresh, restores lost packets with the parity, decodes with VideoToolbox and checks the red and blue eye badges of the host's scene. It simulates a headset's display and reports the frame timing and the loss to the host. It exits with code 0 when at least half of the expected frames decode with the right eye colors. A client on this Mac needs no pairing. The ignored app test starts the host the way the window does and connects the probe. The client's ignored tests drive a real host with the client's connection code in a flat window.

The game path without Wine:

```bash
./target/release/cranvr-probe --game --seconds 14 &
./target/release/cranvr-fake-game --control /tmp/cranvr-test/runtime-control.txt --seconds 10
```

`cranvr-fake-game` speaks the runtime's protocol and shares IOSurfaces like the Wine runtime. Its eye badges have swapped colors, so `--game` tells its frames from the test scene.

## End-to-end test

`scripts/e2e.sh` runs the host, a client and an optional game, then writes a JSON report. The report holds every 5-second stats line of the host and the median and worst of each number: the frame rate, the render and encode times and the latency block (see "Latency numbers"). The script exits with 0 when the host and the client both reach 90 percent of the target rate after the first stats line. With the probe it must also show 95 percent of the frames that reached its decoder.

```bash
scripts/e2e.sh --fps 120 --game
scripts/e2e.sh --native-drop 3
scripts/e2e.sh --native-tcp
scripts/e2e.sh --quest SERIAL0000001 --native-port 9961 --seconds 30
scripts/e2e.sh --seconds 14 --wine 'C:\basalt\runtime\d3d11_runtime_smoke.exe' \
    --wine-arg --render-frames --wine-arg 1200
```

`--native-drop` drops media packets for the parity to restore. TCP media carry no parity and lose no packet, so the run refuses `--native-drop` with `--native-tcp`: a drop of 3 percent of the packets there left 58 percent of the frames.

Every program that a run starts, a Windows program or the fake game, fails the run when its log has a FAIL line (`FAIL: ...` or `NAME: FAIL ...`) or when it ends on its own with an exit code other than 0. A program that still runs at the end, such as a game, ends with the run. A test program with a verdict line must end within 10 s of it. Before #169 the modes with a verdict line required only their PASS line, and a plain `--wine` run required nothing of its program: `d3d11_runtime_smoke.exe` failed its own checks before its first frame and the run passed on the host's own scene.

`--openvr-wine` runs `C:\opencomposite\openvr_smoke.exe`, a Direct3D 11 OpenVR program (source: `third_party/opencomposite/tests/openvr_smoke.cpp`), against the real runtime and the probe. It finds OpenComposite through the prefix's OpenVR path file, as a game does, and fails without it. It starts as an application of type Scene, reads the recommended size and the eye transforms (through the vtable in the order of MSVC's callers and through the FnTable), draws a different color in each eye and submits both eyes in every frame, reads the head pose and reads the legacy controller state that the probe scripts (left grip, right trigger at 0.75, button A). It also checks the eye distance. It asks the host for 72 Hz unless `--fps` says otherwise: it tests the path of an OpenVR program, not the rate. It also checks that the display frequency of the headset, as the runtime tells it to a game, is the rate of the host (`--expect-hz`). The program prints the interval of each frame, the frames of each second and the rate once the start has settled.

The frame rate of the program at 120 Hz had two causes. The first was OpenComposite's restart of the OpenXR session. A game restarts it twice at its start (at the first input call and at the first frame), and each restart slept for 250 ms between two looks at the session's state. The first second of a run held 47 to 50 frames instead of 120 (two frames of 300 ms). OpenComposite patch 0003 looks every 2 ms, and the first second holds 97 to 110 frames. Three interleaved runs of 20 seconds at a load average of 15 to 47 made 110.7, 113.4 and 116.0 frames a second with the older OpenComposite and 118.3, 118.5 and 118.7 with the new one. The second cause is the Mac's load. Another build that keeps the Mac busy (a load average above 20) stalls the program for 60 to 120 ms at a time, and `xrWaitFrame` of the runtime then skips a whole frame period. The second-by-second counts show 120 in the quiet seconds and 60 to 100 in the busy ones. The steady rate (seconds 3 to 19) was 119.1 to 119.6 with the new OpenComposite in those runs. This load is the host's neighbours, not a cost of OpenComposite: no steady-state cost of the OpenVR path showed up, and the runs on a loaded Mac differ from run to run. The OpenXR smoke does not print a frame rate to compare with.

`--openvr-overlay` keeps an overlay up for the whole run, as a loading screen does, and checks that the host still counts the frames of the program (OpenComposite leaves the overlay out, since the runtime takes no quad layer). `--openvr-actions touch|vive|both` runs the same program with IVRInput. It writes an action manifest with default bindings (for Touch controllers, for the Vive wand or for both, as a game ships them) to `%TEMP%`, sets it, updates the action set in each frame and reads the actions that the probe's scripted controllers drive: the grab (the left grip), the trigger's pull and click, the thumbstick or the trackpad, the A button (Touch bindings only) and both hands' pose actions, which must follow the probe's script (the left hand stays, the right hand swings, both at the height that the probe's floor gives). It pulses the left hand's haptic output when the grab fires, and the run fails when no pulse reaches the probe. The probe keeps its head still (`--still-head`), so the game's room is the probe's room. Set `CRANVR_HOME` to a stack that `setup-wine.sh` built with OpenComposite.

`--openvr-gl` runs the same program with OpenGL, as Google Earth VR draws: it asks Wine for an OpenGL 3.2 context with the compatibility profile, draws with a shader of GLSL 1.10 and submits one OpenGL texture with both eyes side by side. OpenComposite copies it into the runtime's Direct3D 11 images. The run checks the picture of each eye in the host as `--openvr-wine` does: a run made 72.0 frames a second at 72 Hz with a blue upper half in the left eye and an orange one in the right eye.

`--openvr-arg --threads` makes the program call OpenVR from a second thread for the whole run, as Source 2 games do: the poses of every device, the projection of an eye and the controllers' state, or the actions' data with `--openvr-actions`. OpenComposite restarts its OpenXR session at the program's first submit, and the second thread must not see the session that the restart destroys (OpenComposite patch 0016). With patch 0015 the program ended at its first submit with a page fault. With patch 0016 its second thread made 2.9 to 6.3 million calls in 14 s, and the run passed with `--openvr-wine`, `--openvr-vulkan` and `--openvr-actions both`.

`--openvr-arg --scale --openvr-arg 1.118` draws the eyes at 1.118 times the recommended size, as Serious Sam VR does. With `--host-arg --game-scale --host-arg 1` the runtime gets images of 2308x2468, above a Quest 3 eye. At 120 Hz the program made 119.4 to 119.8 frames a second with Direct3D 11 (597 to 599 game frames in 5 s). At the limit of 4128x4416 (`--scale 2`) the host's compose took 2.4 to 2.5 ms of GPU time, against 1.8 to 2.4 ms at 2064x2208, at a load average of 40 to 50. The program's memory grew from 381 MB to 1048 MB, the host's from 63 MB to 66 MB: the images belong to the program. `--openvr-vulkan` runs the same program with Vulkan (`openvr_smoke.exe --vulkan`): it draws on the device that `GetOutputDevice` names and submits an R8G8B8A8 image per eye, which OpenComposite blits into the runtime's B8G8R8A8 images on the GPU. `--openvr-arg --format --openvr-arg bgra` submits B8G8R8A8 images, which OpenComposite copies as they are, and `--openvr-arg --samples --openvr-arg 4` multisampled ones, which it resolves. Each eye is exact black with a gray band down its left edge and a block of the eye's color. `--xr-vulkan [enable2|enable1|array]` runs `C:\basalt\runtime\vulkan_runtime_smoke.exe`, an OpenXR program that draws the same picture with Vulkan into the runtime's images: with `XR_KHR_vulkan_enable2` (the default), with `XR_KHR_vulkan_enable` or with one swapchain of two slices. The run checks the program's verdict, the host's count of game frames (90 percent of the rate in the windows after the first) and the colors of each eye. It works with `--quest` too. Both need a stack that `setup-wine.sh` built with the runtime and the Wine files to test (`CRANVR_HOME`).

`--swapchain-churn d3d11|d3d11-array|vulkan|vulkan-array` is a leak test of the runtime's swapchain images. It runs `C:\basalt\runtime\swapchain_churn.exe`, which creates and destroys a swapchain of three images 1000 times (`--churn-cycles`) with Direct3D 11 or Vulkan, with one slice or two. The images are 333 pixels high, which no game uses, and of a new width each time. The run counts the live global IOSurfaces of that height in every process (`scripts/iosurfaces.py`, which tries the IDs from 1 up) and reads the program's memory footprint (`footprint`) after the first swapchain and after the last one, and counts the surfaces again after the program ended. It fails when a surface of a destroyed swapchain stays, in the program, in the host or in launchd, or when the IOSurface part of the footprint grows by more than a twentieth of what the swapchains had. `--churn-frames` shows each swapchain in one frame and destroys it right after `xrEndFrame`, while the GPU may still draw it: the runtime must keep the images until the GPU is done. A run takes about 15 seconds, most of it Wine's start. Before cranvr's DXMT patch 0019 and runtime patch 0015, each destroyed swapchain of Direct3D 11 left its three surfaces in launchd until the user logged out, and the 22nd Vulkan swapchain of a new size failed. After them, 1000 swapchains left none in each of the four ways; the churn took 0.7 ms a swapchain with Direct3D 11, 4.2 ms with two slices, and 1.0 to 1.5 ms with Vulkan.

`scripts/shared-churn.sh [--cycles N] [--width W] [--height H]` is a leak test of DXMT's shared textures and shared fences, with no host and no headset. It runs `C:\basalt\runtime\shared_churn.exe`. In each of 200 cycles the program makes six shared textures of DXMT's own path (R16G16B16A16_FLOAT, B8G8R8A8 with a legacy handle, mipmaps, two slices with an NT handle, 4x MSAA, a keyed mutex), one IOSurface texture and a shared fence. A second process of the program opens each one and checks its description and color. Then both release everything. At the end the second process must refuse the handle of a released IOSurface texture whose ID names a surface of another size by then. The run counts the names in launchd of both processes (`scripts/launchd-names.py`, which reads `launchctl print gui/UID` and looks each DXMT name up): while they hold the first cycle's objects, after that cycle, after the last cycle and after their end. It also reads the IOSurface part of their footprint. It fails when a name of a released object stays, when a surface stays, or when the surfaces of the processes grow with the cycles. A run takes about 10 seconds. Before cranvr's DXMT patch 0020 each cycle left 8 names in launchd with the memory of its textures: 2 cycles of 64 x 64 left 16 names with 375 KB of surfaces after the program's end, until the user logs out. The released texture's handle also opened on the new surface of another size. With the patch, 200 cycles of 640 x 333 show 8 names while both processes hold the objects. No name stays after a cycle or after the end. The surfaces of both processes grow by 11 MB once while the cycles make 1981 MB. The shared fence goes through a round in each cycle: both processes signal it and wait on it, on the CPU and on the GPU, for a value that the other one signaled (runtime patch 0020). The run fails when the round did not go through in every cycle. Before cranvr's DXMT patch 0021 the second process could not open the fence in any cycle (#161): DXMT kept the fence's name in data that Wine 11.10 holds for resources only.

The same run checks the order of the GPU work of the two processes on the shared textures (#177). Direct3D 11 asks a writer to call `Flush` before another device uses a resource that they share without a keyed mutex. After that the reader sees the writes. Metal orders no work of two processes on a texture. Each process of the program keeps its GPU busy for at least 4 ms before its clears. Neither waits for its own GPU before it hands a texture on. In even cycles the first process takes the handles before its `Flush`, in odd cycles after it. The second process must read every color that the first one flushed. The first one must read the color that the second one wrote back. Last, the second process writes a texture and ends at once: the first one's copy of it must be done within 3 seconds. Before cranvr's DXMT patch 0022 the second process read zeros of rgba16f in the second cycle. With the patch each queue that holds a shared texture serves its event through winemetal's broker. A reader's GPU waits for the writer's chunk that wrote the texture (`dxmt_shared_order.hpp` in the patch says how and why). A texture takes a slot in that order only with its first handle: a game's swapchain images, which go to cranvr-host by IOSurface ID, cost nothing. All colors are right in 200 of 200 cycles. Each process's queue then has two names "DXMT_order_..." in launchd while it lives. The run does not count them as names of released objects. It fails when they grow.

`--wine` runs a Windows OpenXR program in cranvr's Wine stack without sound. Each run of a Windows program fails when the program runs at a nice value other than 0. The cranvr app starts games at normal priority. A test at nice 5 measured a slower game (#155). The probe then counts every frame of the right size, since a real program draws no eye badges, so the run also fails when the host counted no frame of the program. The run starts the program once the client has linked, as a user starts a game after the headset linked. The host writes the stream's view size into the control file before its status line of the link. Before any link the file holds the eye that a Quest 3 would get (#170). With `--quest` and a Quest 3 the run fails when the link writes another size than the one before it. The program gets the variables of BasaltVR's own test with a headset (`runtime/scripts/test-headset.zsh`): `BASALT_EXPECT_VIEW_WIDTH` and `BASALT_EXPECT_VIEW_HEIGHT` with the size of the control file, `BASALT_REQUIRE_HEAD_POSE=1`, `BASALT_EXPECT_IOSURFACE=1` and, with the probe, `BASALT_REQUIRE_CONTROLLER_INPUT=1`. Games read none of them. `d3d11_runtime_smoke.exe` then checks a live head pose, the left controller and its aim pose, swapchains up to 4128x4416, DXMT's IOSurfaces and a render loop whose frames reach the host. Without them it expected the size and the input of BasaltVR's native test daemon. The host gives a game the Touch profile of both hands at its start, also while the controllers sleep, as Unity needs. A Quest on a desk has sleeping controllers, so with `--quest` the program gets `BASALT_ACCEPT_MISSING_CONTROLLER=1` in place of `BASALT_REQUIRE_CONTROLLER_INPUT=1` (runtime patch 0019, #173). The left hand may then have the Touch profile with inactive actions. The program checks the bindings of the profile, and it checks the controller's values and poses only while its actions are active. It waits for no controller. Before, the program waited 30 s for the left controller, and the run failed with no frame of the program. The run fails when the size in the control file changed during the run. `--desktop` starts the host with its desktop panel. The probe then asks for the desktop stream, plays a pointer script (the host only logs its mouse events, as `CRANVR_POINTER_DRY_RUN=1` does) and counts the Mac's sound. It plays no sound: it measures what arrives. The run fails when the probe gets the Mac's sound for less than 80 percent of the stream time.

`--quest` starts cranvr's client on a Quest attached by USB (install it with `scripts/build-client.sh --install SERIAL`). adb keeps its display on without a face in the headset. The script pauses the guardian for the run. It sets the exact old value back at the end, an empty value included, also after a failure, Ctrl-C or a kill with TERM or HUP (`scripts/guardian.sh`). Only `kill -9` leaves the guardian paused. The Quest and the Mac must share a network. The host runs with `--trust-all` on `--native-port` (default 9950). A headset keeps one host key for each address and port. Pick a port that the headset has not used with another host at this Mac's address, such as 9961. The app gets this Mac's address and the room `scene` through its launch extras. The run keeps the host's key in `target/e2e/host-identity.txt`, because a headset refuses a known address with a new key. At the end the run starts the client again for the cranvr app's host on port 9950: at 127.0.0.1 when the app linked that port over the cable, else at this Mac's address. On a port other than 9950 the same launch makes the headset forget the key that it keeps for the run's address (`forget_host_key`), so the next test host at that address finds no old key. A run that ends without its cleanup, such as one killed with `kill -9`, still leaves its key behind. Before a Quest run, the harness reads the device's network over adb. It warns when a VPN on the device routes this Mac's address, when the device uses 2.4 GHz Wi-Fi and when its Wi-Fi link runs below 400 Mbps. Two runs with the same setting differ by up to 5 ms in total, so compare two settings with several pairs and keep every report. The run waits a second after it stops the client and starts it again when it has not linked in 15 s: the headset's home once came to the front after a start right after the stop. Check `uptime` before a run: other programs on the Mac lower the rates.

A phone or tablet runs the phone build of the client against a host on this Mac. Use `adb reverse tcp:9962 tcp:9962` and a host with `--native-port 9962`, or the Wi-Fi address of the Mac.

### Measure a game with a Quest on the desk

`scripts/perf/` holds the tools behind the game measurements.

```bash
scripts/perf/game-run.sh aa2 20
CRANVR_MAX_MSAA=0 scripts/perf/game-run.sh aa-game 20
HZ=240 scripts/perf/game-run.sh uncapped 20
scripts/perf/metal-trace.sh bs
python3 scripts/perf/gpu-by-kind.py target/perf/bs.xml "Beat Saber"
```

`scripts/perf/xr-frame-timing.sh` builds an OpenXR API layer (`scripts/perf/xr_frame_timing.c`), registers it in the prefix as an explicit layer and prints the variable that loads it into one game run: `eval "$(scripts/perf/xr-frame-timing.sh)"` before `scripts/e2e.sh --wine ...` or `scripts/run-game.sh`. `--remove` takes it out of the registry. An explicit layer loads only into a process whose `XR_ENABLE_API_LAYERS` names it. The OpenXR loader under Wine ignores `XR_API_LAYER_PATH`, because Wine's processes run at a high integrity level, so the layer needs the registry. The layer sits between the game, or OpenComposite, and the runtime. Every 600 frames it writes a line "cranvr frame timing" to the game's stderr (`game.log` of an e2e run): the frame rate, the time that `xrWaitFrame` waited, the time from its return to `xrEndFrame` (the game's work on a frame), the time of `xrEndFrame` and the time from `xrEndFrame` to the next `xrWaitFrame` (the game's own waits between frames, such as a frame cap). OpenComposite's `WaitGetPoses` is `xrWaitFrame` and `xrBeginFrame`, so the first number is also the wait of an OpenVR game in `WaitGetPoses`.

`game-run.sh` needs the cranvr app running and a headset that is paired with it. It wakes the headset without a wearer and starts cranvr's client and the game without sound. `CRANVR_HOST=ADDRESS:PORT` gives the client the Mac's address. Without it the client uses the address of its last connection. It prints one summary line of the rates and the latency stages. Then it sets the guardian back to its exact old value, also after a failure or a kill. The proximity sensor stays closed, so the headset stays awake. `metal-trace.sh` records 5 seconds of GPU work of every process on the Mac while a game runs. `gpu-by-pass.py` sums that work per process and per pass. `gpu-by-kind.py` sums it per kind of pass. `display-modes.swift` lists the modes of the external display or holds one for its own run.

### A hand for a test run

A test with nobody in the headset can press the buttons of a game's menu. `CRANVR_TEST_INPUT=FILE` makes the host replace the right controller that the client reports with the one that FILE describes. The host reads FILE about every 30 ms. The file holds `NAME=VALUE` words, such as `turn=100 yaw=12 pitch=25 trigger=1`:

- `yaw` and `pitch` (degrees) say where the controller points, from the direction that the head faces. A positive yaw turns to the left and a positive pitch turns up.
- `trigger` (0 to 1) is the pull. A pull of 0.7 or more clicks.
- `primary`, `secondary`, `stick_x` and `stick_y` press A and B and lean the stick. `stick_click` presses the stick down, the click that a game written for the Vive wand's trackpad reads.
- `grip` (0 to 1) is the grip's pull. A pull of 0.7 or more clicks.
- `x`, `y` and `z` place the grip in meters right, up and forward of the head (default 0.2, -0.35, 0.3).
- `turn` (degrees, positive to the left) turns the game's room about the vertical axis through the head. The game sees the head and both controllers turned. The headset and the probe still see the picture for the real pose. A game that puts its panels at the side of a headset on a desk then shows them in front of it. The turn changes only the poses that go to the game. The poses of the frames stay as the headset sent them.

`CRANVR_EYE_DUMP=FOLDER` writes both eyes of the game's newest frame once a second. A thread of its own writes the files, so the dump costs the frame loop no time: with the files written in the loop, The Thrill of the Fight lost 1 to 2 percent of its frames at 120 Hz. `CRANVR_EYE_DUMP_WIDTH=1500` makes the files as wide as an eye (1444 pixels) instead of at most 640. A test reads the dump, finds a button in the picture, writes the angles of its direction into FILE and pulls the trigger for half a second. The pointer of a game's menu points a little higher than its controller: for the pictures of the probe's eye (a field of 90 degrees), the controller had to point 18.5 degrees above the direction of the button.

### The pages of the settings on a Quest

`cranvr --headless` runs the app with no window, for a test beside the user's app: `CRANVR_HOME` names its folder and `CRANVR_NATIVE_PORT` its port. It starts the host, answers the headset's requests as the window does and saves the settings in its own `app.json`. Each line of its input is a press of the window, as a request in JSON. It watches no USB cable, asks macOS for no permission and moves no window. Its recorder asks adb for the headsets on the cable itself. `scripts/pages-check.sh SERIAL WORKDIR` runs it on port 9961 with a made-up game and the scripted build of the client (`scripted_pointer=pages`): the right controller opens the first page of the Mac's settings from the hand menu, changes a setting there and changes the made-up game's VR system on its Options page. At the end it presses two buttons of the window on the headset's own page (Show or Hide of the stream numbers, and Recenter). The client starts with `save_choices=false`. The script prints the entries of the test app's `app.json` that changed and the client's lines of the walk.

`scripts/ui3d-check.sh SERIAL WORKDIR [CAPTURES]` runs the walk of the 3D menus (`scripted_pointer=ui3d`) in the same way and takes a screen capture while the hand menu is open and while the console shows each page. `scripts/capture-check.py` checks each capture before anyone sees it: it keeps a picture only when at least 40% of its pixels are exact black and at most 15% are other grey pixels, so a picture of the room never stays. `scripts/ui3d-budget.sh SERIAL WORKDIR` measures the Flat and the 3D interface with the hand menu closed and open, with a test host that streams its scene at 120 Hz: the frame rate, the stale frames, the compositor's time, the app's GPU time and the layer count from the runtime's VrApi line (`scripts/vrapi-summary.py`).

### Screen captures of a headset on a desk

A screen capture shows the app only while the headset has a head pose. A headset that lies still on a desk in a dark room gets none from its runtime: its tracking cameras log "Images too dark", the client reports no eye views, the host renders no frame and the system's own picture covers the app. Every capture of that state had 15.8 % exact black pixels, the same with the client stopped (#228). `head_pose` in `scripts/client-start.zsh` reads the frames that the client received in its last second. `scripts/screen-check.sh` and `scripts/sharpness/headset-check.sh` call it after each start and end with exit code 2 and the reason when the headset has no head pose. Such a run needs light in the room or a person who wears the headset.

`scripts/sharpness/headset-check.sh SERIAL WORKDIR CAPTURES CASE...` measures a display's panel in the headset (see "Sharp text on a display's panel" in desktop.md). A test host makes a virtual display with the test pattern. Each case starts the client with the first display's panel at a width and a distance (`display_place`) and, after a colon, the widest picture to ask for (`desktop_width`), such as `1.6,1.5` or `3.0,1.5:2560`. `scripts/sharpness/measure.swift` reads the pattern in the left eye of one capture. Of the patches of the squares' colors, it takes the four whose projection finds the pattern's paper and ink in place, so other patches of those colors in the room do not count. A panel seen at a slant passes. It exits 3 when it finds no pattern.

### Client starts in scripts

A script counts a start of the headset client only when the same client process still runs 3 s after it links to its host (`scripts/client-start.zsh`). A link line alone proves nothing: on 2026-11-23 a client linked, crashed 1 s later and left the user's stream dark for 16 minutes (#145). Every script that starts the client puts the user's client back on 9950 at its end, also after a failure or a stop: `scripts/give-back.sh SERIAL [APK]` installs APK first when it is given, starts the client and checks it the same way. `CRANVR_GIVE_BACK_APK` names that APK for the check scripts. `scripts/start-check.sh SERIAL WORKDIR STARTS [STOP_AFTER] [PORT]` starts the client against a test app again and again and counts the starts that held, crashed, ended with no crash or never linked. It prints the top frames of each crash.

## Other settings of the host

- The eye stream's frames stand on the encoder's time line at the real time between them, at most two frames apart after a pause. VideoToolbox's rate control gives a frame the bits of that time. Before, the frames stood 1 ms apart, so the stream sent 5 to 8 percent of its bitrate (issue #90).
- The eye stream's bitrate follows the link, up to the bitrate that the user set (see "The eye stream's bitrate"). `host/src/tests/eye_quality.rs` measures the quality on the Mac: a moving game picture at 120 Hz rose from 34.5 dB (8.5 Mbps) to 39.5 dB at 40 Mbps and 43.4 dB at 70 Mbps.
- The encoder overlaps up to two frames. A data rate limit over each second keeps the stream at or under the bitrate target. `--strict-rate-control` switches to VideoToolbox's low-latency rate control: even frame sizes, one frame at a time, slower per frame on an M5 (6.1 ms against 3.6 to 5.0).
- `--foveation off|low|medium|high` sets the level of the foveated encoding (see "Foveated encoding"). Off encodes every pixel at full density, with a smaller eye.
- `--pointer-pitch DEG` tilts the pointing ray down from the controller's handle (default -40). It applies to a client that sends no aim pose. A client's aim pose gives the ray as it is.
- A headset with Tailscale that accepts a subnet route for its own network sends its UDP to the Mac through the subnet router, which changes the sender address. The stream may then not arrive. The handshake still works over TCP, so the headset connects, gets no video and leaves after about 5 seconds, again and again. The host reports it after two such connections in a row. The fix is on the headset: exclude the cranvr app from the VPN, or stop using the subnet route there. The host also warns when this Mac reaches the headset through a VPN tunnel of its own. `--tcp` sends the media over TCP to every headset.

### The eye stream's bitrate

The host lowers the eye stream's target when the headset's frames miss their points of the display grid, and raises it slowly while they stay low (`host/src/bitrate.rs`, issue #97). The target stays between 10 Mbps and the bitrate that the user set. The user's setting is the ceiling. Once a second the frame loop counts the frames that the headset reported in that second: shown on time, late, replaced or lost, and those that the host sent and the headset has not reported. A second with 12.5 percent of its frames missed, or with a network time over 1.5 periods, cuts the target at once, by a fifth to a half. A share of 6 percent over 5 s cuts too. Three calm seconds in a row (at most 4.2 percent missed in each) raise the target by a tenth. After a cut the target waits a second, then stays under 90 percent of the level that failed for 30 s. Each new failure of that level doubles the wait, up to 4 minutes. A session over the USB cable starts at the user's setting. A session over a network starts at 100 Mbps at 120 Hz (the same bits a frame at other rates). A headset that shows no stream (Room at Passthrough, no game) reports no frames. It still decodes every frame. After 2 s without reports the target falls to 10 Mbps, and the control starts anew at its start when reports come again. The first second with reports decides nothing: it counts the frames that the headset replaced while it showed nothing, up to 31. A second in which the host sent fewer frames than a quarter of the refresh rate, such as one of a game that loads, decides nothing and keeps the target. After a pause of the stream (the headset's app without the input focus) the next 2 s decide nothing and the target stays.

A game's frame aims for the first point of the display grid after its arrival. The host takes the arrival from the 90th percentile of the network times of the last 64 frames. It took half the round trip before, which left out the time that a large frame spends on the link. At 200 Mbps a frame of 175 KB took 4.5 ms over the cable and 6.5 ms over Wi-Fi against 0.3 and 1.5 ms of half the round trip, and 14 and 48 percent of a game's frames came late.

Measured on a Quest 3 at 120 Hz with the moving fake game (`scripts/e2e.sh --quest SERIAL --moving --native-port 9961`, foveation Off, the user's 200 Mbps), the Mac on Wi-Fi 6 and the headset on the same network or on its USB network:

| | USB network | Wi-Fi 6 |
|---|---|---|
| a frame moves at | about 330 Mbps, plus 0.4 ms | about 330 Mbps, plus 2.3 ms |
| late frames at a fixed 40 Mbps, the old aim | 1.9 % | 7 % |
| late frames at a fixed 200 Mbps, the old aim | 14 % | 48 % |
| late frames at a fixed 120 Mbps, the new aim | 1.2 % | 0 % |
| the target settles at | 200 Mbps, 1.1 to 1.5 % late | 200 Mbps, 0.7 % late |
| the time to the ceiling | from the start | 26 s from 100 Mbps |
| pose to display | 48 to 50 ms at 40 to 90 Mbps, 52 to 57 ms at 200 | 49 to 50 ms at 110 to 160 Mbps, 54 to 64 ms at 176 to 200 |
| a test cap under the target | the first cut 0.9 s after the cap, under the cap after 3 s, no missed frame after 5 s | the first cut 1.1 s after the cap, under the cap after 3 s, at most one missed frame a second after 5 s |

A higher bitrate costs latency: a larger frame takes longer on the link and in the headset's decoder (4.1 ms at 20 KB, 7.1 ms at 175 KB). The user's setting is the trade. While the headset showed no stream the host sent about 10 Mbps, against 25 Mbps at the old cable limit of 40. The old fixed limits were 40 Mbps at 120 Hz over the cable and 12 Mbps over a network. The frames of both links moved at the rate of the link: the issue's note of 150 Mbps over the cable belonged to `adb reverse`. The host's own send of a frame of 175 KB took 0.9 ms. A start at 200 Mbps over Wi-Fi once gave 7 s of network times of 9 to 13 ms with peaks of 257 ms, until the target fell to 112 Mbps, while a later run carried 200 Mbps from a start at 100. The Wi-Fi start of 100 Mbps comes from the first case.

A send that blocks costs frames, not latency (#157). Over `adb reverse` the media go over TCP, and a write waits while the link carries less than the stream. The frames from the encoder wait for the send in a queue of at most 3 frames (`host/src/send_queue.rs`). A frame that comes to a full queue makes the oldest go, with the frames after it up to the next key frame: each refers to the frame before it, and the headset numbers the frames that it gets one by one. The queue then takes key frames only and asks the encoder for one. The bitrate's control counts the dropped frames as missed and cuts. A second whose frames the queue dropped is no sign of a headset that shows no stream. Before, the channel to the send had no bound. On a steady link at most one frame waited in each second over the USB network, over `adb reverse` and with the probe over TCP. The stats line counts the frames that waited and went (`send queue: up to 1 frames waited, 0 dropped`).

Measured on a Quest 3 at 120 Hz with the moving fake game at 200 Mbps and foveation Off, a test host on port 9961, and 4 s of `slow=60` (each send waits for its frame's time at 60 Mbps, as a TCP write does), the time from the pose to the display of each second:

| | before the slow part | the seconds of the slow part | the seconds after it |
|---|---|---|---|
| USB network, no bound | 50 to 57 ms | 483, 1158, 1848 ms | 2487, 532, 47 ms; 325 frames went out in one second |
| USB network, the queue | 49 to 53 ms | 113, 118, 108 ms | 67, 47, 44 ms |
| `adb reverse`, no bound | 55 to 58 ms | 450, 1145, 1794 ms | 2361, 969, 50 ms; 304 frames in one second |
| `adb reverse`, the queue | 49 to 55 ms | 113, 113, 98 ms | 67, 46, 44 ms |

Without the bound the target fell to 25 Mbps after the slow part, since the late frames of the pile went on missing their points. With the queue it fell to 50 Mbps in the slow part, had no late frame in the seconds after it and rose again 3 s later. `adb reverse` carried 200 Mbps on this Mac (a frame of 146 KB in 5 ms), where it carried about 150 Mbps in the measurements of #97.

`CRANVR_TEST_BITRATE=FILE` is a knob for tests (`host/src/test_bitrate.rs`). The host reads FILE about every 100 ms. `fixed=MBPS` holds the target. `cap=MBPS` drops the frames that a link of that rate could not carry within 50 ms, as a full queue drops them. `slow=MBPS` makes each send wait for its frame's time on a link of that rate, as a TCP write over a slow link waits. With the variable set the host logs a line for each second of the link: the frames encoded, dropped before the send and the most that waited, reported, late and replaced, the time from the pose to the display, the network time, the size of a frame, the send time and the target. Without it the line comes only with a change of the target.

The window's stats line names the target: "28 Mbps sent of 40 now, 200 set". The console's main page in the headset shows it after the latency while the headset shows the stream: "120 Hz, 120 fps, 45 ms, 80 of 200 Mbps". The stream numbers in the headset show it as the stream's target. The stats line of the host keeps `mbps` for the target and `mbps_set` for the user's setting.
